Architecture

How it fits

Every click in the lab went through one service, bnk-inference-adapter. It owns the Inference Gateway API, turns each call into Gateway API, Gateway API Inference Extension (GAIE) and BNK objects, and collects per-request usage records that the BNK iRule sends it. One Helm chart installs it. Two small helpers sit next to it: frontier-proxy for Amazon Bedrock and calypso-relay for F5 AI Guardrails.

Production split

Who owns what

Everything the lab did, sorted by who runs it in production.

Lambda side

  • API gateway: route /api/v1/inference-* and /api/v1/network-firewall-* to the adapter on :8080, after Lambda's own key check
  • Key service that answers the introspection contract
  • Instance inventory: model-server pods or relays labelled lambda.ai/instance and lambda.ai/role, and the instance list
  • Billing pipeline reading the usage records
  • Console section built on the contract (the lab portal is the reference UI)
  • AWS account for frontier models, and the Calypso project for guardrails

Adapter side (Helm chart)

  • bnk-inference-adapter: owns the contract, renders Gateway API, GAIE and BNK objects, collects usage and firewall events
  • frontier-proxy: OpenAI-compatible front for Bedrock
  • calypso-relay: holds the guardrail token, so the iRule sideband stays plain HTTP to an IP
  • RBAC scoped to lambda-ie and f5-bnk, NetworkPolicy, a 200Mi PVC
  • Values: VIP range, sideband URLs as ClusterIPs, prices, the usage flush token

BNK side (unchanged)

  • BNK 2.4 with the Gateway API and GAIE CRDs
  • GatewayClass f5-gateway-class for the CNEInstance
  • lambda-ie in CNEInstance.spec.eppNamespaces
  • F5 registry pull secret copied into lambda-ie
  • A routable VIP range for endpoint addresses

The iRule has no DNS and no TLS

BNK iRules open sidebands as plain TCP to an IP. Give the introspection and guardrail URLs as http://<ClusterIP>:<port>/path, the form the lab ran. The target must speak plain HTTP and be reachable from TMM. Anything HTTPS gets a small relay in the cluster, which is why calypso-relay and frontier-proxy exist.

The Kubernetes objects are the truth

The adapter keeps no data-path state. Gateways, routes, pools and iRules are the state of every endpoint. SQLite holds only policy config, usage records and benchmark runs. Delete endpoints through the API, and never uninstall the chart with endpoints still running.

OpenAPI 3.1

The contract

There are two contracts, one per API. The Inference API covers endpoints, policies, usage and benchmarks. The Network firewall API covers policies, address and port lists, log destinations and events. Both are proposed extensions of the Lambda Cloud API v1.10.0 and follow its conventions on purpose, so they can sit in the same spec:

  • Resources under /api/v1/inference-endpoints, actions under /api/v1/inference-endpoint-operations/…. That's the same split as instances and instance-operations.
  • Every response is wrapped in {"data": …} and every error in {"error": {"code", "message", "suggestion"}}, using Lambda's codes (global/invalid-api-key, global/object-does-not-exist, global/invalid-parameters).
  • Bearer keys come from the same API keys page.

The one addition outside that pattern is PATCH …/policies/{kind}. BNK enforces enabled policies in the data path in a fixed order: api_auth → guardrails → token_quota → ai_load_balancing.

Policy kinds

ai_load_balancing, token_quota, guardrails, api_auth, model_schedule, network_firewall. Each moves through off → applying → on (or error with a reason).

Chat outcomes

served, downgraded, auth_rejected, guardrail_blocked, quota_blocked, error. Gateway refusals come back as results with 200, not as API errors.

The sideband contracts

BNK talks to three services from inside the iRule. These are the only integration points on the data path, and each is plain HTTP or TCP to an IP address.

What BNK does

API call → BNK objects

Gateways, iRules and NetPolicies live in namespace f5-bnk. Routes, Services, InferencePools and F5EPPs live in lambda-ie. Every object is labelled lambda.ai/endpoint=<id> and app.kubernetes.io/managed-by=bnk-inference-adapter, so one label selector finds everything an endpoint owns.

API callWhat BNK creates or changes
POST /inference-endpointsGateway ie-<id>-gw (VIP from 172.16.201.110–129, listener http :8000), HTTPRoute ie-<id>-route, Service ie-<id>-rr (round-robin), InferencePool ie-<id>-main + F5EPP ie-<id>-main-epp, F5BigCneIrule + NetPolicy ie-<id>-policy (metering fragment, always bound)
POST /inference-endpoints/{id}Adds or removes the lambda.ai/ie-<id>: main|fallback label on the chosen relay pod templates. Pools and the Service follow by selector.
DELETE /inference-endpoints/{id}Removes every object labelled lambda.ai/endpoint=<id> and the endpoint's pod labels
PATCH …/policies/ai_load_balancingRepoints rule 1 of ie-<id>-route to InferencePool ie-<id>-main (on) or Service ie-<id>-rr (off)
PATCH …/policies/token_quota
mode block		Re-renders the iRule with the quota fragment. Over-budget requests get 429 global/quota-exceeded. No extra objects.
PATCH …/policies/token_quota
downgrade, AI LB off		InferencePool ie-<id>-fallback + F5EPP ie-<id>-fallback-epp, Service ie-<id>-fb-rr as rule 0 of ie-<id>-route, selected by the iRule pool command
PATCH …/policies/token_quota
downgrade, AI LB on		Second Gateway listener http-fb :8001, HTTPRoute ie-<id>-fb-route → InferencePool ie-<id>-fallback + F5EPP, NetPolicy ie-<id>-policy-fb. BNK answers 307 to :8001 with X-Quota: downgraded.
PATCH …/policies/model_scheduleRe-renders the iRule with the schedule fragment (TMM reads the hour). Off-peak goes through the same fallback objects as a downgrade, or to the frontier listener when the off-peak model is on Bedrock. X-Schedule: peak | off_peak
FRONTIER_MODELS (adapter setting)Third Gateway listener http-frontier :8002, HTTPRoute ie-<id>-frontier-route → Service frontier-proxy (Amazon Bedrock), NetPolicy ie-<id>-policy-frontier. BNK answers 307 to :8002 with X-Frontier: bedrock.
PATCH …/policies/guardrailsRe-renders the iRule with the guardrail fragment (sideband scan, fails closed)
PATCH …/policies/api_authRe-renders the iRule with the auth fragment (sideband key introspection)
POST …-operations/reset-usageNo objects. Clears the adapter's usage store and quota counters.
POST …-operations/benchmarkRepoints rule 1 of ie-<id>-route between Service and InferencePool for each phase, then restores it

Data path

The iRule

Policies you turn on produce one composite iRule per endpoint, ie-<id>-policy. It's rendered from fragments in a fixed order. Metering is always in it.

auth→guardrail→quota→metering · always

A NetPolicy attaches it to the endpoint's listener:

NetPolicy ie-<id>-policy
kind: NetPolicy
metadata:
  name: ie-3f9a1c0b7d2e-policy
  namespace: f5-bnk
spec:
  extensionRefs:
  - group: k8s.f5net.com
    kind: F5BigCneIrule
    name: ie-3f9a1c0b7d2e-policy
  targetRefs:
  - group: gateway.networking.k8s.io
    kind: Gateway
    name: ie-3f9a1c0b7d2e-gw
    sectionName: http
Read them on the cluster
# the iRule text
kubectl get f5-big-cne-irules $EP-policy -n f5-bnk \
  -o jsonpath='{.spec.iRule}'; echo

# the binding to the listener
kubectl get netpolicies $EP-policy -n f5-bnk \
  -o jsonpath='{.spec}' | jq .

For Lambda's environment. Your BNK, your key service, your API gateway, your console and your billing. Every lab stand-in is replaced. Values come from values-production.yaml.

  4. Key introspection Lambda identity

    One contract, two callers. The adapter checks API keys with it (HTTPS is fine). The auth iRule checks data-path keys from TMM (plain HTTP, reachable from TMM). sub is who usage is metered against, and role decides who may change things. Errors and 3 s timeouts fail closed. An HTTPS-only key service gets a plain-HTTP proxy in lambda-ie, locked to TMM and the adapter, called by ClusterIP.

    contract
    POST /introspect   {"token": "<key>"}
200 {"active":true,"sub":"<user>","role":"admin"|"member"}
200 {"active":false}

    manifests/introspect-stub.yaml answers this from a Secret, for trying the install before your key service is wired. Don't run it in production.

Auth in the lab

The browser never holds a key. The console's nginx injects one server-side, only for same-origin requests that carry X-Lambda-Console: 1 and no Authorization header. A cross-site page can't send the custom header without a preflight, which nginx never approves.

Auth in production

Use the console's existing session. Whatever your API gateway turns it into, the adapter introspects the key and needs the right sub and role back.

Types

Generate with npx openapi-typescript contracts/inference-gateway.openapi.yaml. Gateway refusals in chat (auth_rejected, guardrail_blocked, quota_blocked) are 200 results, so show them as outcomes, not errors.

Before go-live

Security hardening

The chart is the one the lab ran. Two points to close before production. Neither needs a chart change. The full admission policy is in INSTALL.md.

Keep lambda-ie for model servers only

The adapter may patch Pods and Deployments in lambda-ie to move endpoint-membership labels. A patch can change more than labels, so run nothing else there, and add a ValidatingAdmissionPolicy that lets the adapter's ServiceAccount change labels only. Run scripts/conformance.sh after applying it.

Limit who can create HTTPRoutes

Endpoint Gateways use allowedRoutes.namespaces.from: All. Anyone who can create an HTTPRoute could attach to an endpoint's listener. Grant httproutes create only to the adapter and platform admins. Narrowing it in the adapter is a later code change.

Backups

Snapshot the PVC. The reconcile loop keeps cluster objects in line with the stored policy config, so a restored volume brings endpoints back to their last configuration.

Upgrades

helm upgrade with a new image. The API is down for a few seconds (one replica, Recreate). The data path isn't, because BNK keeps serving what's already applied.

Removing it

Delete every endpoint through the API, then helm uninstall. The adapter removes its Gateways, routes, pools and iRules. Nothing else will.
